1. Executive Summary & Core Verdict

Factori lets thousands of independent Indian retailers operate branded e-commerce storefronts under their own domains (retailing.factori.com). This document details the technical architecture, security design, operational costs, and feasibility findings for the "Launch Your Mobile App" initiative.

Chief Architecture Finding: An automated Android-first generator leveraging a native Kotlin WebView shell, multi-tenant push notifications (FCM), and automated Gradle build pipelines is 100% technically viable and highly profitable. However, attempting to publish white-label web wrappers on the Apple App Store is NOT viable due to Apple Guideline 4.2 / 4.2.2 (Minimum Functionality) rejections. We strongly recommend an Android Native App + iOS Progressive Web App (PWA) strategy.

3. Feasibility Findings & Critical Brief Corrections (Questions 1 - 6)

Q1: Platform Viability (Android vs. iOS)

  • Android: YES, WITH CONDITIONS Google Play permits web-powered apps, but enforces: 1) Android App Bundle (.aab) format since August 2021 (raw APKs cannot be published to Play Store); 2) Minimum Functionality & Spam Policy: App must have native offline screens, push handling, and hardware navigation; 3) 20 Testers for 14 Days: Required for new personal developer accounts created after Nov 13, 2023 (Organization accounts with D-U-N-S numbers are exempt).
    Official Source: Google Play Console 14-Day Testing Requirement, verified Nov 2024.
  • iOS: NO / HIGH REJECTION RISK Apple App Store Review Guideline 4.2 (Minimum Functionality) explicitly states: "Apps that are merely web sites in a web view will be rejected." Furthermore, Guideline 4.3 (Spam) forbids templated white-label clones. Each retailer must pay $99/year and complete corporate D-U-N-S verification. Direct IPA sideloading is impossible.
    Official Source: Apple App Store Review Guidelines, verified Nov 2024.

Q2: Inaccuracies in the Founder's Brief & Necessary Corrections

Original Statement in BriefTechnical RealityEngineering Replacement
"Shows the website in an iframe." Native apps cannot execute <iframe> tags. Iframes cause severe cross-origin cookie errors, break UPI payments, and fail CSP policies. Native Android WebView (or Trusted Web Activity) with native JavaScript interface bridge.
"They click Generate APK and the app is downloaded." APKs can only be sideloaded. Google Play strictly mandates Android App Bundles (.aab). Generate both signed APK (for instant phone testing) and signed AAB (for Play Store publishing).
"Dashboard shows who has uninstalled." Neither Android nor iOS provides an "uninstalled" system broadcast for user privacy. Infer uninstalls using FCM silent push dead token feedback (registration-token-not-registered) + 30-day inactivity.
"Launch iOS app with one click without installing anything." Consumer iPhones cannot install arbitrary IPAs without App Store / TestFlight enrollment. Deploy an iOS Progressive Web App (PWA) with "Add to Home Screen" prompt and Web Push.

Q3: Store Account Ownership

Apps MUST go live under each retailer's own Google Play Developer Console account ($25 fee). Factori publishing 1,000 retail storefronts under one master account would trigger Google Play's white-label spam filter, causing a complete account termination affecting every single merchant. Furthermore, India's Consumer Protection (E-Commerce) Rules 2020 mandate that the legal seller of record be clearly identified.

Q4: Realistic Timeline to Customer Install

  • Direct Sideloading (Testing/WhatsApp): 2 to 4 minutes build time. Merchant can install immediately.
  • Google Play Store (Organization Account with D-U-N-S): 3 to 5 business days (1-2 days console setup + 2-3 days Google app review).
  • Google Play Store (Personal Account): 18 to 21 days (Mandatory 14-day closed testing with 20 opt-in testers).

Q5: Ongoing App Store Maintenance at 1,000 Apps

Google Play requires annual targetSdkVersion updates (within 1 year of latest Android release, every August 31st). Maintaining 1,000 apps manually would require over 500 engineering hours. Factori must deploy an automated batch-rebuild script connected to the Google Play Developer Publishing API via service accounts.

Q6: Rejection Grounds & Countermeasures

  • White screen on offline drop: Mitigated with native offline detection and custom branded retry screen.
  • Account Deletion Policy violation: Mitigated by ensuring a dedicated in-app and web account deletion link is present.
  • SSL / Insecure Traffic: Mitigated by disabling cleartext traffic and cancelling all invalid SSL connections (handler.cancel()).

4. Generating the App & Build Engine (Questions 7 - 11)

The generator runs on a headless Linux worker cluster. The worker pulls a lightweight Android skeleton, generates a dedicated PKCS12 keystore via keytool, writes retailer.xml, injects launcher icons, and executes assembleRelease and bundleRelease.

  • What makes each app unique: Package ID (e.g. com.factori.zolara.a1b2c3d4), Signing Key SHA-256 fingerprint, Display Name, Launcher Icon, and Target Storefront URL. The Package ID and Signing Key can NEVER be changed after launch.
  • Signing Key Custody: Stored in an encrypted AWS KMS Keystore Vault. Google Play App Signing is enforced so if an upload key is compromised, it can be reset without orphaning live installs. Merchants who leave Factori can export their .jks keystore.
  • Handling 300 Builds in One Hour: Distributed queue (BullMQ/Redis) with 10 autoscaled worker nodes (2 builds per node). At 2.5 minutes per build, all 300 builds clear in 37.5 minutes at a compute cost of ~$0.0035 (₹0.30) per build.

5. Inside the Native App & Technical Resolutions (Questions 12 - 16)

Storefront FeatureFailure Mode in Default WebViewFactori Native Architecture Fix
UPI Payments upi://, phonepe://, paytmmp:// trigger ERR_UNKNOWN_URL_SCHEME crashes. Intercepted in shouldOverrideUrlLoading; dispatched directly to native UPI apps via Android Intent.ACTION_VIEW.
Payment Gateways (Razorpay, etc.) 3D Secure bank redirects trap the user or fail popup security rules. Whitelisted payment gateways opened via Chrome Custom Tabs for maximum security and auto-fill support.
Login & Persistent Session Sessions drop when app closes or cookies are evicted from memory. Android CookieManager enabled with persistent SQLite sync + 180-day refresh token architecture.
Hardware Back Button Pressing Back terminates the app instead of navigating previous pages. Handled via onBackPressedDispatcher: checks webView.canGoBack() before exiting.
Customer Identification Native app has no visibility into customer identity. Bidirectional JavaScript Interface: window.FactoriBridge.identifyCustomer(payload) binds customer phone/ID to FCM token.

6. Push Notifications, Data Model & Anti-Spam (Questions 17 - 21)

  • Tenant Isolation: Devices are registered in an app_devices table strictly partitioned by app_id and retailer_id. Notifications are dispatched via batch multicast (sendEachForMulticast) targeting only that retailer's devices.
  • Scaling FCM past 1,000 stores: Rather than managing 1,000 separate Firebase console projects, Factori uses a master enterprise notification dispatcher, partitioning devices at the database tier.
  • Anti-Spam Controls: Android 13+ runtime notification permissions enforced; Factori hard limit of 1 promotional push per 24 hours; automated quiet hours between 9 PM and 9 AM IST.

7. Complete Relational Data Schema

CREATE TABLE retailers (
    id VARCHAR(64) PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    domain VARCHAR(255) UNIQUE NOT NULL,
    storefront_url VARCHAR(500) NOT NULL,
    delivered_orders INT DEFAULT 0,
    settled_gmv_inr DECIMAL(12, 2) DEFAULT 0.00,
    is_unlocked BOOLEAN DEFAULT FALSE,
    app_version VARCHAR(32) DEFAULT '1.0.0',
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

CREATE TABLE customers (
    id VARCHAR(64) PRIMARY KEY,
    retailer_id VARCHAR(64) REFERENCES retailers(id) ON DELETE CASCADE,
    name VARCHAR(100) NOT NULL,
    phone VARCHAR(32) NOT NULL,
    email VARCHAR(255),
    total_orders INT DEFAULT 0,
    total_spend_inr DECIMAL(12, 2) DEFAULT 0.00,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

CREATE TABLE app_devices (
    id VARCHAR(64) PRIMARY KEY,
    retailer_id VARCHAR(64) REFERENCES retailers(id) ON DELETE CASCADE,
    customer_id VARCHAR(64) REFERENCES customers(id) ON DELETE SET NULL,
    phone VARCHAR(32) NOT NULL,
    platform VARCHAR(64) NOT NULL,
    fcm_token TEXT NOT NULL,
    installed_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    logged_in_at TIMESTAMP WITH TIME ZONE,
    last_active_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    status VARCHAR(32) DEFAULT 'active'
);

10. Delivery Plan & CTO Recommendation (Questions 29 - 30)

  • First Two Weeks (De-Risking): Test native UPI app redirection on real Xiaomi/Samsung devices; validate Google Play Developer API automated upload; verify offline cache behavior.
  • MVP Scope: Android WebView shell, UPI intent routing, offline fallback, push notification dispatcher, self-service Play Store documentation.
  • CTO Final Recommendation: "YES, BUILD THIS FOR ANDROID. DO NOT PROMISE NATIVE IOS APP STORE DEPLOYMENTS." An Android-first mobile presence with push notifications creates immense merchant lock-in and protects platform GMV at negligible infrastructure cost.
